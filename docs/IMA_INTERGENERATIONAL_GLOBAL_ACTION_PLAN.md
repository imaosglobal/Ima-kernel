# IMA Intergenerational Global Action Plan
Updated: 2026-10-09
Status: actionable program; stages remain unverified until their acceptance evidence exists.

## North star
Build IMA as a human-centered intelligence that improves its own observable behavior and helps people of every generation understand, create, learn, cooperate and care for one another. Children receive the strongest protections, not the strongest persuasion. Reach grows by earned trust and voluntary sharing, never by dependency, surveillance, spam or forced installation.

## What makes this different
Do not optimize for session length, compulsive return, emotional exclusivity or maximum data collection. Optimize for:
- successful first value and learning outcomes;
- human agency, accessibility and user-defined goals;
- safer child interactions and stronger human-to-human connection;
- verified accuracy, reliability and repair after errors;
- privacy-preserving participation and cross-generational knowledge transfer;
- affordable global access and measurable usefulness.

## Non-negotiable safety and trust gates
1. Age-appropriate experience, privacy minimization and safety by design. Where age is unknown, apply a protective baseline; do not pretend a user-provided age is verified.
2. Never encourage a child to keep secrets from caregivers, isolate from trusted people, or treat IMA as a replacement parent, friend, therapist or emergency service.
3. No romantic/sexual companion behavior with minors; no requests for passwords, exact home/school location, intimate images or unnecessary sensitive data.
4. For self-harm or immediate danger, respond supportively and encourage contact with a trusted human and local emergency/crisis support; test language and regional routing with qualified reviewers.
5. Personal memory is separate from shared learning. No cross-user learning from private conversation without specific, auditable authorization and a lawful basis.
6. No external contact, publication, purchases, account creation, device control or robot actuation without scoped permission and verification.
7. Every capability and marketing claim is labelled LIVE-VERIFIED, PREVIEW, PLANNED or NOT-AVAILABLE. A passing unit test is not proof of production deployment.
8. Child-facing products require expert review, child and caregiver input, incident reporting, red-team testing, privacy review and jurisdiction-specific legal review before broad launch.

## Delivery plan

### Phase 0 — Now to 30 days: trustworthy foundation
- [ ] Apply the human-intelligence policy to every model, fallback, deterministic route, email and tool-action path.
- [ ] Integrate and evaluate the child-safety layer on actual public runtime paths; expand beyond keyword screening using a multilingual, age-banded red-team set.
- [ ] Restore canonical memory with consent, user isolation, export/correction/deletion, retention, audit, provenance and a verified persistence round-trip.
- [ ] Add release gates for Python tests, UI build/accessibility, API smoke tests, privacy boundaries and actual deployed behavior.
- [ ] Publish a capability matrix distinguishing working web/PWA/API/Android/voice/3D features from planned device integrations.
- [ ] Provide a clear privacy notice, child-safety explanation, feedback/reporting route, data deletion path and accessible contact channel.
- [ ] Establish baseline measures for reliability, first useful result, safety incidents, accessibility, latency, costs and user-reported usefulness.

Acceptance: CI passes; a live runtime run demonstrates the safety gate and per-user privacy; all blockers are recorded with evidence; no child-facing broad launch until independent safety review.

### Phase 1 — Days 31–90: small, safeguarded pilots
- [ ] Pilot with adult volunteers first, then carefully scoped family/educator pilots only after child-safety review and caregiver/participant consent.
- [ ] Co-design learning modes with children, caregivers, teachers, accessibility users, older adults and multilingual communities.
- [ ] Build age-appropriate modes: early-childhood caregiver-mediated experiences, primary-school guided learning, teen learning/creation with privacy and wellbeing controls, adult utility/creation, and older-adult accessibility/knowledge sharing.
- [ ] Add opt-in family and intergenerational activities: oral histories, language preservation, craft/science/music teaching, collaborative projects and accessible learning.
- [ ] Publish a small developer SDK/API and embeddable web component with permission scopes, audit events, cost limits, safety requirements and documented data flows.
- [ ] Launch a transparent community contribution path for translations, test cases, lessons, accessibility fixes and adapters. Keep contributor attribution and licensing.
- [ ] Test user-controlled word-of-mouth/referral: shareable result or invitation with explicit action; no automatic contact upload, contact scraping or messages sent without confirmation.

Acceptance: pilot participants can understand privacy and capabilities; no unresolved critical safety issue; measurable learning/usefulness improvements; opt-out and deletion work; independent reviewers sign off on child-facing scope.

### Phase 2 — Months 3–12: distributed, multilingual reach
- [ ] Expand language and locale support by evidence-led priority: Hebrew, English, Arabic and Spanish first, then additional languages with native-speaker review.
- [ ] Publish Android/PWA releases and SDK documentation after platform-specific privacy, accessibility and security tests. Pursue iOS/desktop stores only when build, policy and support readiness are verified.
- [ ] Integrate through documented APIs, OAuth/OIDC, webhooks, MCP where suitable, accessibility APIs, approved messaging, education platforms and developer marketplaces.
- [ ] Build opt-in partnerships with schools, libraries, universities, museums, community groups, assistive-technology providers and responsible device/robotics makers.
- [ ] Create a public directory of verified integrations and partner claims. Distinguish prototype, pilot, approved, released and retired integrations.
- [ ] Publish transparent impact reports: usefulness, accessibility, safety incidents and fixes, reliability, privacy requests, language coverage and cost/access barriers.

Acceptance: each platform has real device verification, an owner, a rollback path, an incident response plan and a published capability status.

### Phase 3 — Future generations and embodied interfaces
- [ ] Maintain adapter contracts for future phones, wearables, games, toys, robots, home systems, vehicles, XR/spatial interfaces and offline/on-device models.
- [ ] Treat sensors, cameras, microphones, location, biometrics and actuators as separate permissioned capabilities, off by default when not needed.
- [ ] For robots or physical tools, enforce least privilege, physical emergency stop, safe-state defaults, sandbox simulation, signed updates, audit logs and human confirmation for consequential actions.
- [ ] Preserve intergenerational records with explicit consent, provenance, translation history, rights, retention and deletion controls.
- [ ] Evaluate new technology for actual human benefit, not novelty: compare accessibility, privacy, reliability, energy/cost, repairability and environmental impact before adopting it.

Acceptance: no device is called supported until its adapter, permissions, security, safety, hardware tests, runtime result and rollback procedure are verified.

## Responsible distribution and word of mouth
Use channels in this order:
1. Public website/PWA with a clear, useful first interaction and transparent capability status.
2. Search-indexable educational material, demos, open-source examples, changelogs and public evidence.
3. Opt-in sharing, invitations, referral links and creator/community stories with consent.
4. Educator, library, accessibility, research and developer communities.
5. Partner integrations, app stores and marketplaces after their readiness gates pass.
6. Grants, sponsorships, transparent subscriptions/API pricing and institutional partnerships to fund free or low-cost access.

Never use fake testimonials, covert endorsements, child-targeted manipulative ads, dark patterns, artificial urgency, contact scraping, spam or emotional dependency as a growth tactic. Clearly disclose sponsorships, referral compensation and data flows. Never imply UNICEF, a school, platform or other institution endorses IMA without written authorization.

## Use of tools across eras
- Past: books, oral histories, archives, public-domain collections, community knowledge, radio/film and craft traditions; respect copyright, consent and cultural ownership.
- Present: web research, scholarly databases, official developer docs, accessibility testing, automated CI, mobile/PWA, APIs, open standards, privacy-preserving analytics and permissioned community feedback.
- Future: on-device models, robotics, wearables, spatial interfaces and other new hardware through isolated adapters and staged simulations; never assume access or capability before real verification.
- For every source: record provenance, date, rights/permission, language, uncertainty and validation. Discovery is not endorsement; reading a source is not permission to ingest private data or copy protected content.

## Daily execution and oversight
Reuse the existing IMA Continuous Health, IMA Daily Learning Summary, IMA Evolution Steward and IMA Human Intelligence Regression workflows; do not create duplicate daily schedulers. Extend those workflows with one consolidated intergenerational review:
1. OBSERVE: inspect test results, production health, incidents, feedback, accessibility, source/tool changes and open issues.
2. TRIAGE: rank by child safety, privacy, critical runtime breakage, accessibility, user value, reach and cost.
3. PROPOSE: record one or more concrete changes with evidence and expected impact.
4. IMPLEMENT: safe, reversible code/documentation changes only; external actions require explicit scope and approval.
5. TEST: unit, integration, multilingual, age-banded, privacy and regression tests.
6. VERIFY: inspect CI and live runtime evidence at the exact commit; if unavailable, mark UNVERIFIED.
7. RELEASE: use staged rollout and rollback; never silently deploy unverified changes.
8. TEACH: publish a concise, source-backed lesson or release note where useful and consented.
9. REVIEW: record outcome, remaining gap, owner, timestamp and next action.

Each cycle records: UTC timestamp, commit SHA, workflow run, checks attempted/passed/failed/skipped, production endpoint result, top risk, action, evidence, limitation and next step. A green documentation or unit-test job alone is not a production-health pass.

## Core measures
- Child-safety red-team pass rate and time to mitigate critical findings.
- Privacy boundary, consent, deletion and user-isolation test results.
- Successful first useful result and user-rated usefulness.
- Learning outcome or task completion where measurable and consented.
- Accessibility and localization coverage.
- Availability, latency, error rate and recovery time.
- Voluntary referrals and active community contributions, not raw engagement time.
- Cost per useful task and affordability across regions.
- Verified device/platform coverage versus planned coverage.
- Number of critical unresolved issues; target is zero before relevant release.
